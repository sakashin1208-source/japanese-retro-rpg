## 2. 未対応で残っている課題

### ⑤ テクスチャフィルタが Nearest のまま

**該当**: `project.godot:124` `textures/canvas_textures/default_texture_filter=0`

SPEC §12 B-10 で「本作はグラデーション主体の描画であり、最近傍法にすると縮小時に劣化する」と確定済みだが、Nearest が維持されている。改修設計案は「ドット絵をピクセルパーフェクトに描画するため維持」と記載するのみで、確定仕様との差異についての判断根拠が示されていない。

**影響**: `stretch/mode="canvas_items"` では2D内容がウィンドウ解像度で直接ラスタライズされるため、非整数倍スケール（ほぼ全てのウィンドウサイズ）でスプライトのピクセルが間引かれ、移動時にちらつく。

**選択肢**:

| 案 | 設定 | 得失 |
|---|---|---|
| A | `default_texture_filter=1`（Linear） | 縮小が滑らか。確定仕様と整合。ドットのエッジは甘くなる |
| B | `stretch/mode="viewport"` ＋ Nearest | 真のピクセルパーフェクト。整数倍以外では黒帯が増える |
| C | 現状維持 | 判断として有り得るが、**SPEC §12 B-10 を改訂して根拠を残すこと** |

いずれを採るにせよ、確定仕様と実装が食い違ったまま放置しないことを推奨する。

> **相互依存の注意**: `tests/test_runner.gd:52` が `filter == 0`（Nearest）を、`:102` が `aspect == "keep"` を**合格条件としてアサートしている**。案A/Bを採用する場合は、この2箇所も同時に更新しないとテストが失敗する。テストが仕様の代わりに実装の現状を固定してしまっている状態なので、判断確定後にテスト側も追随させること。

`fonttools` が利用できない環境のため、**TTFのcmapテーブルを標準ライブラリで直接解析**し、本作が使用する全文字の収録状況を実測した。

| 検査対象 | 検査文字数 | 結果 |
|---|---|---|
| `assets/data/master_data.json` 全文 | 658字 | **全収録** |
| GDScript内の日本語リテラル | 554字 | **全収録** |

## 4. 申し送り事項

### (1) `window/stretch/aspect="keep"` が作業ツリーで消えている

コミット済みの `godot/project.godot` には `window/stretch/aspect="keep"` があるが、**未コミットの作業ツリーでは削除されている**。Godotエディタがプロジェクトを保存する際、エンジン既定値と一致する設定を省略するためと推測される（＝既定値が `keep` である可能性が高い）。

意図的な変更ではない可能性があるため、**コミット前に意図を確認すること**。4:3維持を仕様として保証したいなら、既定値と同値でも明示的に残す方が安全である。

### (2) 未pushのコミットが存在する

本報告書作成時点で `main` は `origin/main` より **4コミット先行**している。push は外部送信にあたるため、オーナー承認のうえで実施すること。

### (3) 検証できていない範囲

- **統合テスト73件は実行済み**（§6）。Godot本体を `run_game.bat` から発見し、headlessモードで実測した
- 実機での日本語表示・描画品質の**目視**確認は未実施。フォントの収録状況については §3 の静的検証（cmap解析）で代替した。実際の画面レンダリングの見た目までは確認していない

### (4) 再発防止の観点

課題④（章移動の前進のみ）は、**Web版 `MenuUI.js:118` で指摘済みの欠陥がGodot版へそのまま移植された**ものだった。移植時は、移植元で未解決の指摘事項を突き合わせるチェックを挟むと同種の持ち込みを防げる。

```
Godot_v4.7.2-stable_win64.exe --headless --path godot tests/test_scene.tscn
```

### 6.1 テスト結果: 申告どおり73件全PASS

```
全 73 件中: 成功 73 件 / 失敗 0 件
>> 全テスト合格 (ALL TESTS PASSED) <<
```

M1〜M4の基盤テスト、受入1〜13（拡張含む）まで**実測でも申告と一致**した。静的解析だけでは確認できなかった実行時の整合性（ダメージ計算・行動順ソート・セーブロード往復・ターゲット選択・章解放判定）が、実際にGodot上で動作することを確認できた。

### 6.2 新規検出: テスト終了時にノードリークが再現する

テストは成功する一方、**プロセス終了時に毎回ノードリークが発生**している。

```
WARNING: 8〜9 ObjectDB instances were leaked at exit
ERROR: 3 resources still in use at exit
```

3回連続実行し、**毎回再現**（8, 9, 9件。件数の微差はテスト内の乱数ダメージ計算による分岐差と推測）。

**切り分けのため実施した検証**: `queue_free()` が実際に処理されるまでフレームが進んでいない可能性を疑い、`_ready()` の最後（`quit()` 直前）に `await get_tree().process_frame` を5回挿入して再実行した（検証後は元のファイルへ復元、差分ゼロを確認済み）。

```
5フレーム待機後も: WARNING: 7〜8 ObjectDB instances were leaked at exit
```

**結論**: フレーム待機では解消しない。単なる「解放待ちの未消化」ではなく、**参照が残り続けている実質的なリーク**である。

**該当箇所の推定**: 第1巡で軽微指摘した「`queue_free()` 直後に同一コンテナへ `add_child` する、毎ターンの全ノード再生成パターン」（`battle_scene.gd` の `render_sprites()` / `render_party_cards()` / コマンド一覧・技一覧の再構築）が引き続き残っており、これが原因である可能性が高い。テストは `battle_scene` を10回近く `instantiate()` → `queue_free()` しており、この往復のたびに数個ずつ蓄積している計算になる。

`--verbose` を付けると当該警告自体が出力されなくなる（Godotのリソースキャッシュ挙動が変わるためと推測、原因未特定）ため、リークオブジェクトの型名までは特定できていない。

**実害の見積もり**: テスト実行1回（戦闘シーンの生成・破棄を計10回程度）で7〜9個。実際のプレイでは戦闘シーン全体は `SceneManager.change_scene_to_file()` で丸ごと破棄されるため、**このリークがテスト特有のパターン（`instantiate()`直呼び出し）に起因するのか、実プレイのシーン遷移でも起きるのかは未確認。** 後者であれば長時間プレイでのメモリ増加につながるため、次の1点を推奨する。

**推奨対応**: `battle_scene.gd` の `render_sprites()` / `render_party_cards()` を、ノードの全削除・再生成ではなく既存ノードのプロパティ更新方式へ変更する（第1巡で軽微指摘した内容と同一）。合わせて、実プレイでの章移動やエンカウントを十数回繰り返した状態でのメモリ計測（`Performance.get_monitor(Performance.OBJECT_COUNT)` 等）を一度行い、実害の有無を確定させることを推奨する。

## 6. 総括

第1巡で検出した重大3件・中4件のうち、**静的解析ベースでの未対応は⑤（テクスチャフィルタ）1件のみ**。特に以下は質の高い対応だった。

- `ui_accept` の使用を **0件** まで徹底したこと（機械的に検証可能な形で完了させた点）
- 施錠理由の文言を `MasterData` から**動的取得**する設計にしたこと。設計案の段階では実在しない「夜叉狐」等の固有名詞がハードコードされていたが、動的取得により世界観の齟齬が構造的に起きなくなった
- Theme リソース化により、フォント・サイズ・**黒フチ取り（SPEC §10.2）** を一括で満たしたこと

実機での統合テスト実行（§5）により、**申告73件の全PASSは実測でも確認できた**一方、**新たにノードリークを実測で検出**した。これは第1巡で軽微指摘した「毎ターンの全ノード再生成」パターンが原因である可能性が高く、テスト成功の裏で解消されていなかった。
