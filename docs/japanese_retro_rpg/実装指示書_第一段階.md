### 4.1 確定した仕様（2026-08-31 決定済）

初版で「判断を仰ぐ項目」としていた事項は、以下のとおり確定した。**この内容で実装すること。**

#### (1) 章移動の条件（SPEC §12 B-8 の決着）

**前進**は進行条件を満たした場合のみ解放する。

| 移動 | 解放条件 |
|---|---|
| 第一章 → 第二章 | 第一章ボス「九尾の妖狐・茜（幻影）」撃破 |
| 第二章 → 第三章 | 第二章ボス「妖魔将・酒呑童子」撃破 **かつ** 神具「八咫の鏡」「八尺瓊勾玉」を両方取得 |
| 第三章 | 「真・九尾の天狐・茜」撃破でエンディングへ遷移（章移動なし） |

**後退**は、一度解放された章へは自由に往来できる（回復・レベル上げのため）。

> **実装上の必須要件**: 解放状態は**新規のセーブ項目を設けず、既存フラグから導出すること。**
> ```js
> const isUnlocked = ch =>
>   ch === 1 ? true :
>   ch === 2 ? state.bossDefeated.youko :
>   ch === 3 ? (state.bossDefeated.shuten && state.artifacts.mirror && state.artifacts.magatama) : false;
> ```
> メモリ上の `visitedChapters` 等で保持すると**ロード後に往来できなくなる**。導出方式なら自動的に整合する。

#### (2) モジュール構成

**ES Modules（`<script type="module">`）を採用**する。`file://` では動作しないため、動作確認は必ずローカルサーバ経由で行う。
SPEC §1.1 は本決定に合わせて改訂済み（「ビルド不要」は維持、「ローカルサーバ不要」は撤回）。

#### (3) 描画設定 — `pixelated` にしないこと

```
ctx.imageSmoothingEnabled = false   // キャンバス内部：等倍でクリスプに描画
CSS  image-rendering: auto          // 画面への縮小：スムーズ補間
```

**SPEC §12 B-10 の初版指摘（`pixelated` に統一せよ）は撤回された。**
本作はグラデーション主体の描画であり、`pixelated` にすると縮小時にちらつき・ジャギーが発生して劣化する。
詳細は改訂後の SPEC §12 B-10 を参照。

#### (4) デバッグ用スイッチ（推奨）

章移動に進行条件が付いたため、第三章のテストには6体のボス撃破が前提となり、イテレーションが著しく遅くなる。
`?debug=1` 等で全章解放・ボスフラグ設定ができる開発用スイッチを用意すること（本番ビルドでは無効化）。

### 6.1 マイルストーン間の依存関係（2026-08-31 追記）

計画レビューで判明した、順序を誤ると受入ゲートを通過できない依存。

#### (1) `ItemUI` は M7 に置く — M8 ではない

M7 の受入ゲートは「**全コマンド**がキー・タップの両方から到達可能」であり、これには「どうぐ」が含まれる。
したがって `ItemUI` が M8 にあると **M7 を通過できない**。

かといって「戦闘用」と「マップ用」で別々に実装してはならない。
**C-2（戦闘の「どうぐ」未配線）と R-4（`useItemOnMap` 未配線）は、まさにこの二重管理から生まれた不具合である。**

| マイルストーン | `ItemUI` に関する作業 |
|---|---|
| **M7** | `src/ui/ItemUI.js` を**戦闘・マップ共用**として実装。戦闘側から配線 |
| **M8** | **マップ側の呼び出し口のみ追加**（`MenuUI` → `ItemUI`）。UI本体は作らない |

これにより M7/M8 の分離意図（M7＝戦闘コマンドの到達性、M8＝永続化とマップ側UI）は保たれる。

#### (2) エンカウント経路は M4 と M6 に分けて配置する

初版のマイルストーン定義では、**ランダムエンカウント判定と TRANSITION 演出がどこにも割り当てられていなかった**。
これが欠けるとマップから戦闘への遷移が成立せず、M9 の「通しで探索」が達成できない。

| マイルストーン | 作業 |
|---|---|
| **M4** | `encounterGrid`（エリア種別）と `eventGrid`（ボス配置）を**マップ構築時に埋める**。判定ロジックはまだ不要 |
| **M6** | 歩数ベースのエンカウント判定（SPEC §7.2）と TRANSITION 演出（SPEC §3.1、35フレーム）を実装し、**マップ→戦闘を接続する** |
| **M9** | 第二・三章のマップと `eventGrid` を追加。ロジックは M4/M6 のものを流用する |

#### (3) スプライト命名規則は M2 で確定する

命名統一（チェック項目15）の作業自体は M3 だが、**M2 の `MasterData` が `spriteKey` を参照する**。
M2 着手時点でどちらの体系（`npc_elder` 系か `npc_village_head` 系か）に寄せるかを決めないと、M3 で手戻りが生じる。

#### (4) 戦闘コマンドメニューにも `{label, handler}` 方式を適用する

チェック項目9（メニューのデータ定義化）は `MenuUI`（M8）だけの話ではない。
**M7 の戦闘コマンドメニューにも同じ方式を適用**し、キー操作とタップが同一の `handler` を呼ぶようにすること。

## 7. 検証方法（必須）

### 7.1 経路テストを必ず書く

現行実装では**「関数は実装したがUIに配線していない」不具合が2回発生**している（戦闘の「どうぐ」、`useItemOnMap`）。
いずれも**関数の単体テストは通っていた**。同じ失敗を繰り返さないため、以下を必須とする。

> **内部関数を直接呼ぶテストだけでは不合格とする。**
> 疑似入力を InputManager に流し込み、**メニュー入力 → 状態遷移 → 効果発生**までを通しで検証すること。

実装例は `DESIGN_技術設計書.md` §11.3 を参照。

### 7.2 受入テスト（7項目）

すべて経路テストとして固定すること。**全項目が現行実装で実際に壊れた箇所である。**

1. 戦闘勝利 → ステータス画面に Lv / HP / EXP が反映される
2. 戦闘敗北 → 蘇生後にHPが回復しており、次の戦闘で行動できる
3. 「はじめから」→ Lv1・所持金0・第一章・全ボス未撃破に戻る
4. セーブ → リロード → ロード → 章・座標・ボスフラグ・神具・所持金が一致
5. **戦闘とマップの両方から**全アイテムが使用でき、所持数が減る
6. 素早さの高いキャラが先に行動する（行動順ソートが機能している）
7. **物理技が通常攻撃より強い**（ダメージ式の分岐が機能している）

#### テスト実行環境

`src/tests/index.html` を作成し、**ブラウザ上で実行**すること。
`GraphicsEngine`（`document.createElement('canvas')`）・`localStorage`・`AudioContext` に依存するため、
素の Node では動作しない。jsdom や node-canvas の導入は「依存ゼロ」原則に反するため採用しない。

#### 乱数を含むテストの注意（テスト7）

ダメージ式には乱数項がある（通常攻撃 ±2、技 ±3）。Lv1疾風 vs から傘小僧の実測値は
**通常 22〜26 / 居合い一閃 39〜45** と変動するため、**期待値を固定値で比較すると不定期に失敗する**。

対策のいずれかを採ること。

- 乱数生成関数を注入可能にし、テスト時は `() => 0` を渡して無効化する（推奨）
- 100回試行の平均値で比較する

#### エイリアス検証の機械化（M3 の受入ゲート）

「エイリアス0件」は目視ではなくアサーションで判定する。

```js
for (const [name, dict] of [['tiles', gfx.tiles], ['sprites', gfx.sprites], ['portraits', gfx.portraits]]) {
  console.assert(new Set(Object.values(dict)).size === Object.keys(dict).length,
    `${name}: 同一canvasを指すキーが残存している`);
}
```

## 8. やってはいけないこと

| # | 禁止事項 | 理由 |
|---|---|---|
| 1 | `main` ブランチへの直接コミット | 現行版を常に動く状態で保つため |
| 2 | 現行の `index.html` / `js/` の削除・移動・リネーム・上書き | §9 の承認境界。参照用に残す |
| 3 | 移行とリファクタの同時進行 | 「動かない原因が移行か設計変更か」の切り分けが不能になる |
| 4 | 敵スプライトのアートを作り直すこと | 品質は既に十分。劣化リスクのみが残る |
| 5 | 単体テストのみで「完了」と報告すること | §7.1 の失敗パターンの再発 |
| 6 | 仕様書の数値（ステータス・EXP・威力）を独断で変更すること | バランス調整は §4.1 と同様、確認を要する |
| 7 | 外部ライブラリの追加 | 「依存ゼロ・ビルド不要」は本プロジェクトの中核要件 |

## 9. 承認が必要な操作（`AGENTS.md` 準拠）

以下は**しんちゃんから「はい」または「承認」の明示的な同意を得てから**実行すること。
「OK」「GO」等の他の表現は承認とみなさない。

- 削除 / 移動 / リネーム / 上書き（現行 `js/` や `index.html` の入れ替えを含む）
- 外部送信（`git push` を含む）
- 本番反映（`main` へのマージ、公開）
- 他プロジェクトへの干渉

緊急時であっても、承認なしの実行は認めない。
