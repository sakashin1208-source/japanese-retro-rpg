## 4. 最初から正しく作り込む項目（チェックリスト）

現行コードに残る欠陥、および設計上の改善点。**再構築時に最初から正しく実装する。**
各項目の詳細な実装方式は `DESIGN_技術設計書.md` の該当節を参照。

| # | 項目 | 要件 | 設計書 |
|---|---|---|---|
| 1 | **技の物理/魔法分岐** | `skill.type === 'physical'` なら ATK基準、`'magical'` なら MATK基準で計算式を切り替える。**現行は分類を無視しており、Lv1疾風は通常攻撃28に対し居合い一閃20とMPを払うほど弱い** | §4.4 |
| 2 | **バフの全員初期化** | 味方・**敵の双方**に `buffAtk` / `buffDef` / `buffSpd` を `1.0` で初期化。片方でも欠けると行動順ソートが NaN になる | §4.3 / §4.5 |
| 3 | **バフのダメージ式への一貫適用** | `buffAtk` を通常攻撃だけでなく**技のダメージにも**適用する（現行は技に乗らない） | §4.4 |
| 4 | **敵AIの重み付き抽選** | `actions[].rate` を出現率として重み付き抽選する。現行は均等ランダムで rate を無視 | §4.6 |
| 5 | **敵行動タイプの効果分岐** | `heal`（敵の自己回復）/ `defend` / `buff_self` を、味方へのダメージではなく本来の効果として処理する | §4.6 |
| 6 | **マスターデータと状態の分離** | `MASTER`（不変・Object.freeze）と `GameState`（可変）を分離。`state.reset()` 一行で新規ゲームが成立すること。**初期値をコード内に二重に書かない** | §1.2 |
| 7 | **戦闘結果の書き戻し** | `Scene.exit()` に書き戻しを置き、勝利・敗北・逃走の**全経路で必ず通る**ようにする | §4.3 |
| 8 | **敗北時の回復** | 全滅後は必ずHP/MPを回復してから復帰する。回復しないと再戦闘で即敗北の無限ループになる | SPEC §6.5 |
| 9 | **メニューのデータ定義化** | メニュー項目を `{ label, handler }` で定義し、**キー操作とタップが同じ handler を呼ぶ**。分岐を二重に書かない。起動時に handler の有無を assert する | §5.5 |
| 10 | **UIスタック** | 独立booleanフラグではなくスタックで排他制御。B/取消は `popUI()` 一律 | §5.4 |
| 11 | **フレームベース戦闘** | `setTimeout` の入れ子を廃し、経過フレーム数のステートマシンにする。**決定キー長押しで演出スキップ可能にすること** | §4.1 |
| 12 | **ボス配置のデータ化** | 座標ハードコードをやめ、マップ構築時に `eventGrid[y][x] = bossId` を埋める | §5.2 |
| 13 | **章定義の配列化** | `CHAPTERS` 配列にする。`chapter % 3 + 1` のようなハードコードを禁止（第四章の追加を想定） | §5.1 |
| 14 | **BGMの先読みスケジューラ** | `setInterval` 内で直接発音せず、`ctx.currentTime` 基準の絶対時刻で100ms先まで予約する | §6.2 |
| 15 | **スプライト命名の統一** | 現行は同一スプライトが2キーで登録されている箇所が31件（`npc_village_head`/`npc_elder` 等）。**どちらか一方に統一**し、`MASTER` 側の参照も揃える | SPEC §10.1 |
| 16 | **描画設定の統一** | CSS `image-rendering` と `ctx.imageSmoothingEnabled` の方針を一致させる | SPEC §12 B-10 |
| 17 | **フォント読み込み待ち** | `document.fonts.ready` を待ってから初回描画する | SPEC §12 B-13 |
| 18 | **パフォーマンス** | 背景グラデーションはキャッシュ、NPC判定は `npcGrid[y][x]` で O(1)、毎フレームの `filter()` を禁止 | §8.2 |

## 7. 検証方法（必須）

### 7.1 経路テストを必ず書く

現行実装では**「関数は実装したがUIに配線していない」不具合が2回発生**している（戦闘の「どうぐ」、`useItemOnMap`）。
いずれも**関数の単体テストは通っていた**。同じ失敗を繰り返さないため、以下を必須とする。

> **内部関数を直接呼ぶテストだけでは不合格とする。**
> 疑似入力を InputManager に流し込み、**メニュー入力 → 状態遷移 → 効果発生**までを通しで検証すること。

実装例は `DESIGN_技術設計書.md` §11.3 を参照。

### 7.2 受入テスト（7項目）

すべて経路テストとして固定すること。**全項目が現行実装で実際に壊れた箇所である。**

1. 戦闘勝利 → ステータス画面に Lv / HP / EXP が反映される
2. 戦闘敗北 → 蘇生後にHPが回復しており、次の戦闘で行動できる
3. 「はじめから」→ Lv1・所持金0・第一章・全ボス未撃破に戻る
4. セーブ → リロード → ロード → 章・座標・ボスフラグ・神具・所持金が一致
5. **戦闘とマップの両方から**全アイテムが使用でき、所持数が減る
6. 素早さの高いキャラが先に行動する（行動順ソートが機能している）
7. **物理技が通常攻撃より強い**（ダメージ式の分岐が機能している）

### 7.3 実機検証

エミュレータではなく**実機**で確認すること。

- iOS Safari: 初回タップで音が鳴る / D-Padのスライド追従 / セーフエリア / 画面回転
- Android Chrome: 同上
- 60fps を維持しているか（開発者ツールのFPS計測）

### 7.4 報告の作法

**「直った」という宣言だけで完了としないこと。** 各修正について、対象・変更前・変更後・確認結果を記録し、
実際の画面またはテスト出力を証跡として提示する（`AGENTS.md` の視覚設計と自己改善の項に準拠）。
